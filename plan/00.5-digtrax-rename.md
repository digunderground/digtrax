# Phase 0.5 — DigTrax brand rename

## Context

OneTagger is being rebranded to **DigTrax** (DJ slang for crate-digging — "dig for trax"). The first wave (this implementation, kicked off alongside V4 design lock-in) handles only the **visual rename** in the frontend chrome (brand mark, page title, on-screen strings). The deeper rename across crate names, bundle identifier, asset filenames, config-dir migration, and CI artifact names is tracked here as a follow-up batch.

This plan stays additive and reversible. Until the full rename ships, the user-visible app reads as "DigTrax" but the underlying binaries, crate names, repo, and config dir all still read as "OneTagger." This is intentional: the visual brand can land in a single PR, while the deep rename touches 11 crate names + tooling + user data and deserves its own focused merge.

## Current scope (visual only — done in V4 implementation PR)

These are landing in the same PR as the V4 design system:

- [client/index.html](../client/index.html) — `<title>One Tagger</title>` → `<title>DigTrax</title>`
- [client/src/components/LogoText.vue](../client/src/components/LogoText.vue) — replace ONETAGGER SVG with `DIG[TRAX]` HTML/CSS brand mark (DIG in `--color-fg`, TRAX in `--color-accent` with glow)
- App.vue size-dialog copy: "One Tagger requires…" → "DigTrax requires…"

That's it for the visual pass. Everything else stays.

### User config migration (the only non-mechanical bit)
[crates/onetagger-shared/src/](../crates/onetagger-shared/src/) uses the `directories` crate to resolve a config dir. Currently this resolves to:
- macOS: `~/Library/Application Support/OneTagger/`
- Windows: `%APPDATA%\OneTagger\`
- Linux: `~/.config/onetagger/` (or similar via XDG)

After rename, it resolves to `DigTrax` paths. Existing users would lose their settings on first launch.

Add a one-time migration in `Settings::load()`:

```rust
fn migrate_legacy_config() -> Result<(), Error> {
    let new_dir = ProjectDirs::from("com", "DigTrax", "DigTrax")?;
    let new_path = new_dir.config_dir();
    if new_path.exists() { return Ok(()) }  // already migrated or new install
    let old_dir = ProjectDirs::from("com", "OneTagger", "OneTagger")?;
    let old_path = old_dir.config_dir();
    if !old_path.exists() { return Ok(()) }  // no legacy config to migrate
    fs::create_dir_all(new_path.parent().unwrap())?;
    fs::rename(old_path, new_path)?;  // or copy + leave the old in place for safety
    info!("Migrated legacy OneTagger config from {:?} to {:?}", old_path, new_path);
    Ok(())
}
```

Run this once during `setup()` before `Settings` deserialization. Safe to run on every launch (idempotent — checks `new_path.exists()` first).

## Risks

- **The user-agent strings on platform API calls.** Beatport / Discogs / MusicBrainz may have allowlisted the OneTagger UA. Check [crates/onetagger-platforms/src/](../crates/onetagger-platforms/src/) before changing, and consider keeping the legacy UA for those clients with a comment noting why.
- **Config dir migration race condition.** If two DigTrax processes launch simultaneously on first run, both will try to migrate. Wrap the migration in a file-lock (`fs2::FileExt::try_lock_exclusive`) or accept the race as harmless (last write wins).
- **Custom-tag rename feature in Phase 2 vs config dir rename.** Don't confuse them — the config dir rename is one-shot Rust code; the Phase 2 custom-tag-rename feature is in-app file metadata work. They share a vocabulary but are unrelated.
